## A01 — Recovery evidence passes without recovery

Priority: high. Type: qualification defect.
Source: `scripts/qualify.py`, lines 310–335 at the audited PR #12 head.

The fixture writes `.selectu5-journal/tx-qualify01.json`.
The engine reads `RECOVERY_DIRNAME`, which equals `.selectu5-recovery`.
The fixture uses `state` and `entry` fields.
The production journal requires `stage`, `id`, identity fields, and a valid transaction identifier.
Changing only the directory name will not repair the fixture.

The fixture moves the active package into a backup.
The subsequent command creates a fresh package at the empty target.
The check accepts exit zero and version 1.0.1 as recovery proof.
It does not require a recovery action or resolution of the fixture journal.

Independent reproduction reported the recovery check as pass.
Its output contained an installation message but no recovery action.
The fixture journal remained in `.selectu5-journal` with `state: published`.
The fixture backup remained present.
The real journal contained a new completed installation record.

Impact: zero credential reads occurred during a fresh installation, not the claimed pending-transaction recovery.
PR #11's correction therefore still overstates recovery read evidence.
This finding does not invalidate the separate Stage 3 interruption results.

Fix: use a real engine transaction and journal schema.
Assert the recovery action, terminal journal state, restored identity, and preserved content.
Add a regression that fails when the engine ignores the fixture journal.

## A02 — The printed install command loses catalog authority

Priority: medium. Type: user procedure defect.
Source: `scripts/selectu5.py`, `cmd_install` dry-run output.

An offline dry run prints `selectu5.py install ... --yes ... --plan ...`.
The printed command omits `--offline`.
The loader normally selects the remote catalog first.
The remote catalog cannot authorize installation.

The auditor copied the printed arguments into the same extracted candidate CLI.
The command returned 1 with a browse-only refusal.
The refused command fetched no installation artifact.
The new bootstrap harness hides this defect because it constructs an offline command itself.

Fix: print a command that preserves the bundled catalog selection.
Do not present browse-only catalog data as installation authority.
Test the exact command shown to the user.

## A03 — Bootstrap acceptance and retained evidence are incomplete

Priority: medium. Type: qualification gap.
Sources: `scripts/qualify_bootstrap.py` and `.github/workflows/tests.yml`.

The harness accepts a candidate version prefix instead of an exact expected client version.
The evidence omits the candidate ZIP digest, code checkout, platform, and complete predecessor identity.
The installed gate check accepts either True or False.
The repeat check accepts exit zero and the text `already installed`.
It does not measure fetch count or compare the complete tree.
The harness inherits environment settings beyond its skills-root override.
It does not explicitly bind `SELECTU5_CORE_DIR` to the disposable dummy core.

CI creates `bootstrap-evidence.json` and `candidate-record.json`.
The upload paths retain neither file.
This prevents reviewers from retrieving those structured results from the existing artifact uploads.

Fix: bind complete candidate and predecessor identities.
Assert expected gate states for the selected release model.
Prove zero fetches and zero mutation during the repeat operation.
Bind the dummy core explicitly and control unrelated catalog overrides.
Retain partial and final bootstrap evidence on both platforms.

## A04 — Only the first bootstrap hop is qualified

Priority: medium. Type: release scope and acceptance gap.
Sources: `docs/production/BOOTSTRAP-AND-UPDATE.md`, `SPEC.md`, and the bootstrap harness.

The observed flow is external 0.2.6 client to installed 0.2.5 client.
The installed 0.2.5 client has `INSTALL_ENABLED = False`.
The bootstrap harness records this as a passing observation.
It does not prove an enabled installed client or a subsequent update.

The document requires a new external ZIP for later updates.
This is a manual external-client procedure, not authority acquired by the installed client.
Even an enabled installed client retains its old bundled catalog.
The document calls the chain self-sustaining without qualification of another hop.
SPEC.md states production qualification is complete and enablement is shipped while PR #12 remains unmerged.

Fix: distinguish the limited first hop from full update qualification.
State that each update requires a newly obtained, independently reviewed external client.
Obtain Mike's decision on that release model before enablement acceptance.
Keep future published-artifact qualification blocked until the artifact exists.
Do not invent a source commit or digest for an unpublished release.
